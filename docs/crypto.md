Crypto Module Overview
======================

The top-level `crypto` module contains three groups of functions: digest hashing, digital signatures and deterministic identities. The digital signature part is the main part of the module, and it depends on the digest hashing interfaces. The deterministic identity part depends on the digital signature part and is not strictly necessary to reside in this module, but it is put together with the other two parts for convenience. Usually, the protocol data types interact with digest hashing interfaces, the protocol implementations interact with digital signature interfaces, and the protocol users (e.g. top level binaries) interact with deterministic identity interfaces.

The digest hashing part defines the canonical form and algorithm of digest hashing in this codebase: 32-byte array produced with `sha2::Sha256`, typed `Digest`. Protocol data types should implement `UpdateHash` in order to be hashed, and the implementations of `UpdateHash` can be easily composed. On the consumer side `DigestHash` produces digest hashes, which is blanket implemented for all types implementing `UpdateHash`. `UpdateHash` and `DigestHash` correspond to `Hash` and `BuildHasher`.

Note that the digital signature interfaces do not use `impl DigestHash` but `impl UpdateHash` because they require "the general capability of being hashed" instead of "can be turned into SHA256 hash value" on their input data types. Indeed they produce SHA512 hash values for ED25519 scheme. User should always implement `UpdateHash` instead of directly implement `DigestHash`.

The digital signature part encapsulates several digital signature schemes into a unified type family, i.e., public key, secret key and signature. Protocol implementations are provided with these unified types of public and secret keys (which are further collected into a `PeerConfig`) and do not need to care about the concrete signature scheme underneath. The unified signature interfaces are `sign` and `verify`, with a `verify_digest` if the `Digest` is manually obtained by the caller.

The deterministic identity part can programmatically produce the necessary public and secret keys for a participate to sign and verify messages, easing the evaluation setup. All participates should be preallocated with a unique index, and these indexed participates are called peers. A peer can construct a `PeerConfig` with its own index, which contains its own secret key and the public keys of all peers. To verify a remote message the peer can select the verifying public key with remote peer's index and call `verify`.
